# Решения

## 1. Фронтенд: React + TypeScript

**Дата:** 2026-11-22

**Вопрос.** На чём делать интерфейс локального приложения для 2–10 человек?

**Варианты.**
1. Статический HTML, который собирает `make_report.py` (как было).
2. Страницы на шаблонах FastAPI (Jinja) без сборки.
3. React + TypeScript + Vite.

**Критерии.** Интерактивность (добавление друзей, синхронизация, удаление с подтверждением,
состояния загрузки и ошибок); строгие типы для JSON-контракта; не усложнять; знакомый
инструмент с большой экосистемой.

**Решение.** React + TypeScript (Vite). Вариант 1 не умеет действий и входа. Вариант 2 проще,
но интерактивные состояния получаются хрупкими без типов. TypeScript ловит расхождения с
контрактом API при проверке `tsc`. Графики сделаны на CSS и SVG без библиотек, зависимостей
минимум.

**Цена.** Появляется Node и сборка, два процесса при разработке. Принято.

## 2. Хранилище: SQLite

**Дата:** 2026-11-22

**Вопрос.** Где хранить прослушивания и список людей?

**Варианты.**
1. SQLite-файл (`sqlite3` из стандартной библиотеки).
2. PostgreSQL.
3. CSV/JSON-файлы.

**Критерии.** Локальный запуск без установки сервера; уникальность прослушиваний и транзакции
(удаление человека целиком); объём данных (десятки тысяч строк); совместимость с уже
собранной `data/flow.db`.

**Решение.** SQLite без ORM. Один файл, нет сервера, `UNIQUE` и транзакции из коробки, база
из первого скрипта продолжает работать. Весь SQL собран в `storage.py`. PostgreSQL избыточен
для 2–10 человек, файлы не дают транзакций и ограничений уникальности.

**Цена.** Один писатель за раз и файл на диске. Для локального использования подходит; при
деплое нужен постоянный том и один процесс.

## 3. Публичные заявки друзей

**Дата:** 2026-11-22

**Вопрос.** Как друзьям передать ник, не добавляя публичных данных и не открывая лишнего?

**Решение.** Один публичный адрес `POST /api/signup`, выключенный по умолчанию
(`SIGNUP_ENABLED`). Требует согласие, проверяет через Last.fm, что ник существует и профиль
открыт, пишет заявку со статусом `pending`. Анна принимает или отклоняет заявку в админке.
Ответ одинаков для новой, повторной заявки и уже добавленного человека, чтобы адрес не раскрывал,
кто есть в системе. Защита от злоупотреблений: honeypot, лимиты длины и частоты, потолок
ожидающих заявок. Контакт стирается после решения.
